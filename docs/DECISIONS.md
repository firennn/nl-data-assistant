# Decisions

Short log of design decisions. Newest last.

| Date | Decision | Reason |
|---|---|---|
| 2026-10-01 | Use SQLite as the database | Zero setup, one file, enough for about 100k orders; easy for three people to rebuild locally. |
| 2026-10-01 | Use the Olist Brazilian E-Commerce dataset | Real, anonymized data with 9 related tables, so questions need real joins; about two years of orders gives enough weekly history for trends and forecasting. |
| 2026-10-01 | Do not commit raw data or the database; rebuild with a script | Keeps the repository small, respects the dataset license (CC BY-NC-SA 4.0) and makes the build reproducible. |
| 2026-10-01 | Three independent read-only safety layers (validator, read-only connection, SQLite authorizer) | SQL comes from a model, so a single regex check is not enough; each layer blocks writes on its own. |
| 2026-10-01 | Modules communicate only through `shared/`, the database and listed public entry points | Lets three people work in parallel with few merge conflicts; interfaces are documented in ARCHITECTURE.md. |
| 2026-10-01 | Provider-independent LLM wrapper with a free-tier primary provider and an optional fallback provider | Keeps cost at zero for a student project; the fallback covers rate limits; providers can be added or removed in one file. |
| 2026-10-01 | Scripted `FakeProvider` and a fixture database for tests | Tests are fast, deterministic and run in CI without API keys or the full dataset. |
| 2026-10-01 | `ChartSpec` is library-independent; Plotly renders it in one place (`shared/charts.py`) | The agent decides what to show; the dashboard and HTML reports draw it the same way. |
| 2026-10-01 | Revenue = sum of `order_items.price` for orders not canceled or unavailable (freight excluded) | One shared definition so the agent, reports and evaluation give the same numbers. |
| 2026-10-01 | Download the dataset with `kagglehub` (anonymous) with a manual CSV fallback | No Kaggle account or token needed for anyone on the team; still works offline with CSVs in `data/raw/`. |
| 2026-10-01 | Drop review comment text, keep only a `has_comment` flag | Free text can contain names or other personal details; scores are enough for the analysis. |
| 2026-10-01 | Aggregate geolocation to one row per zip prefix (mean coordinates, most common city) | The source has about 1M noisy points with many duplicates; one row per prefix makes a clean join key. |
| 2026-10-01 | Keep all orders and statuses instead of filtering | Filtering is a question-level choice (e.g. revenue excludes canceled orders); the database stays a faithful copy. |
| 2026-10-01 | Store timestamps as ISO text | SQLite has no datetime type; ISO text sorts correctly and works with `date()`, `strftime()` and `julianday()`. |
| 2026-10-01 | Build into a temporary file and replace the database only after all checks pass | A failed or interrupted build never leaves a broken database behind. |
| 2026-10-01 | Leave out sample values for id columns in the schema text | Hash ids carry no meaning for SQL generation and cost tokens on every request. |
| 2026-10-02 | Agent replies in JSON with an explicit action (`sql` or `clarify`) | The agent can tell answers from follow-up questions without guessing from free text, and malformed replies can be detected and retried. |
| 2026-10-02 | Ask a clarifying question only when readings differ a lot; otherwise state the assumption | Too many questions make the assistant tiring to use; stated assumptions keep answers transparent. |
| 2026-10-02 | Retry failed SQL with the database error message, at most 2 extra attempts | Most generation errors (wrong column, syntax) are fixed once the model sees the error; a cap bounds cost and latency. |
| 2026-10-02 | Never retry unsafe SQL | A request to change data must not be rephrased until it slips through; the user gets a clear refusal instead. |
| 2026-10-02 | Rule-based chart selection instead of asking the LLM | Deterministic, testable and free; the rules cover the common result shapes. |
| 2026-10-02 | Business rules (revenue, distinct customers, data date range) in the system prompt | Keeps answers consistent with the definitions used by the reports and evaluation. |
| 2026-10-02 | Separate LLM call for the explanation, with a plain summary as fallback | The explanation is based on the actual result rows, and a failed explanation never loses a correct answer. |
| 2026-10-02 | Retry temporary LLM errors inside the provider (server busy, per-minute limits), but fail fast on a used-up daily quota | Busy spells are short and a retry usually succeeds; waiting on a daily quota only wastes time, so the fallback or another model is used instead. |
| 2026-10-02 | Default model `gemini-3.1-flash-lite` instead of the larger Flash model | In testing, the larger model's free tier allowed only 20 requests per day (about 10 questions) and was often overloaded; Flash-Lite answered the test questions correctly with a larger free quota. |
| 2026-10-02 | Reserve extra output tokens for the model's internal reasoning | Newer models count reasoning tokens toward the output limit; without headroom short replies could come back empty. |
| 2026-10-01 | Weekly report metrics live in a registry (`reports/metrics.py`), one decorated function per metric | Adding a metric is a one-file change, and the report, tests and exports pick it up automatically. |
| 2026-10-01 | A report week is the 7 days ending on `week_end` (inclusive), compared with the 7 days before | The dataset ends in 2018, so the week is always explicit instead of based on today's date. |
| 2026-10-01 | Reviews and on-time delivery are counted in the week the review was written or the order was delivered | The weekly numbers then describe what happened that week, instead of changing later as older orders get delivered or reviewed. |
| 2026-10-01 | New customers are counted by their first order that is not canceled or unavailable | Matches the revenue definition, so a canceled first order does not count as gaining a customer. |
| 2026-10-01 | A metric with nothing to measure in a week (no orders, reviews or deliveries) is NaN and shown as "n/a" | Avoids reporting a misleading 0 for an average or a rate. |
| 2026-10-01 | Daily anomalies use a rolling z-score against the previous 28 days (threshold 3), with no look-ahead | Simple to explain and test; 28 days smooths out weekday effects; on the full data it flags Black Friday 2017 (z = 24) and only a handful of other days. |
| 2026-10-01 | Days whose baseline has zero spread are not flagged | Avoids division by zero and infinite scores at the start of the data; this limit is documented in `reports/anomalies.py`. |
| 2026-10-01 | Week-over-week changes of 20% or more are flagged separately from daily anomalies | A slow drift across a week does not show up as a daily spike, but managers still want to see large weekly moves. |
| 2026-10-01 | Anomaly thresholds live in one `AnomalyConfig`, and daily series and detectors in registries in `reports/anomalies.py` | Thresholds can be tuned in one place, and adding a series or detector is a one-function change. |
| 2026-10-01 | Report charts are a registry in `reports/charts.py` that returns a `ChartSpec` plus data, rendered only by `shared.charts.render_chart` | Adding a chart is a one-function change, and the HTML report and dashboard draw charts the same way. |
| 2026-10-01 | The revenue trend reuses the Revenue metric for each week | The last point of the chart always matches the revenue number in the KPI table. |
| 2026-10-01 | Category and state charts show the top 10 for the report week, ties sorted by name | Keeps bar charts readable (there are 27 states and over 70 categories) and the order deterministic. |
| 2026-10-01 | `ReportChart` moved to `reports/charts.py` and is imported into `reports/weekly_report.py` | Avoids a circular import between the chart and report modules; `weekly_report.ReportChart` still works. |
| 2026-10-01 | Forecast weekly revenue with damped-trend exponential smoothing (Holt), compared against a naive baseline (last week's value) | About 85 weeks of data is too short for yearly seasonality; a damped trend follows the level without extrapolating growth too far. Both models are plain Python, so no new library is needed. |
| 2026-10-01 | Evaluate with a rolling-origin backtest over the last 20 weeks (horizon 4), never a random split | Each forecast uses only the weeks before it, like a real weekly run. MAE and MAPE are reported for both models. |
| 2026-10-01 | Keep the stronger model only if its backtest MAE is lower; the baseline wins ties and is used when history is too short | The report always says whether the model beat the baseline. On the full data Holt is about 4% better (MAE 39,085 vs 40,601 BRL), but not in every backtest window, so the margin is small. |
| 2026-10-01 | 80% forecast interval = forecast +/- 1.28 x backtest RMSE at each horizon | The range reflects how wrong the chosen model has actually been on this data, and widens with the horizon. |
| 2026-10-01 | `python -m modeling.train` retrains and writes the model and metrics as JSON to `modeling/artifacts/` (gitignored) | Retraining is one command, and results are reproducible without committing generated files. |
| 2026-10-01 | The executive summary prompt gets a short list of computed facts, never raw rows | Keeps the prompt small and free of personal data, and the LLM can only describe numbers the report already computed. |
| 2026-10-01 | Every number in the LLM summary is checked against the facts (allowing rounding); any unknown number replaces it with a plain summary built from the facts | The report never shows an invented figure, even if the model ignores the instructions. |
| 2026-10-01 | If the LLM is unavailable (no key, rate limit, empty reply), the report uses the plain summary instead of failing | The weekly job still produces a complete report; `summary_source` records which summary was used. |
| 2026-10-01 | `build_report` takes optional `db_path`, `llm` and `config` arguments, and `WeeklyReport` gains `metric_changes`, `summary_source` and `facts` | Tests run on the fixture database with a scripted LLM, and the extra fields are additions, so existing callers are unchanged. |
| 2026-10-01 | The HTML report is one file with inline styles and Plotly loaded once from its CDN | Small files (about 30 KB) that open in any browser and in the dashboard; all text is HTML-escaped. |
| 2026-10-01 | Each report run also writes a JSON file with the same results | The dashboard and other tools can read the numbers without parsing HTML. |
| 2026-10-01 | `generate_report(week_end)` returns the HTML path, the JSON path and the summary as a dict; `run_weekly` and `python -m reports.export` use it | One entry point for the dashboard, the command line and scheduled runs. |
| 2026-10-01 | PDF export is left for later; the HTML report can be printed to PDF from a browser | A good PDF needs a new library (for example matplotlib) in requirements.txt, which the team should agree on first. |
| 2026-10-01 | Scheduling examples (cron, Windows Task Scheduler, GitHub Actions) are documented in `reports/README.md` instead of an active workflow | The data ends in 2018, so a real schedule adds little now; adding a workflow is a team decision. |
| 2026-10-01 | Document the report and forecast in a separate `docs/REPORTS_AND_MODELING.md` | Keeps the module description, sample output and model results in one page owned by the reports/modeling owner; the README can link to it. |
| 2026-10-01 | PDF export with matplotlib (`reports/pdf.py`), added to requirements.txt | matplotlib writes multi-page PDFs by itself, so it works on Windows and in CI without a browser; static Plotly export would need an extra image engine. Charts are redrawn from the same data as the HTML report. |
| 2026-10-02 | Project goal: users can query their own data. They upload a CSV or SQLite file, the app builds a read-only database from it, and the chat page (through the agent) answers questions about it. The report and evaluation pages stay Olist-only as the demo. | Shows that the assistant works on any tabular data, not only on the dataset it was built for. The report metrics and the evaluation questions depend on the Olist schema, so those pages keep using it. |
| 2026-10-02 | Split of the upload work: owner1 makes the agent prompts generic, adds a dataset profile (an optional `profile` argument to `SQLAgent`, defaulting to Olist), adds safety limits and `data/upload.py` (CSV first, then SQLite). owner3 builds the upload page and the privacy notice after owner1's part is merged. | The dashboard builds against a finished, tested interface, and existing callers of `SQLAgent` keep their current behaviour. |
| 2026-10-02 | Uploaded databases leave sample values out of the schema text by default | Sample values from user files can contain personal data, and the schema text is sent to the LLM provider API with every question. |
| 2026-10-02 | Agent prompts are generic; the Olist business rules, currency, date range, examples and filter wording moved to `OLIST_PROFILE` in `shared/profiles.py` | The same agent works on any database. The Olist prompts are unchanged apart from line wrapping and the currency name, so existing answers and the evaluation are not affected. The profile lives in `shared/` because the reports use the same definitions. |
| 2026-10-02 | Without a date range in the profile, relative periods ("last month", "recent") are relative to the latest date in the data, found with `MAX` on the date column | Uploaded data can end at any date; using today's date would return empty results for older files. |
| 2026-10-02 | `DatasetProfile.include_samples` defaults to `False`; only `OLIST_PROFILE` turns it on | A new profile never sends sample values to the LLM provider API by accident; when samples are off they are not even read. |
| 2026-10-02 | Generic prompt examples use a made-up `sales` table, and the prompt says so | Examples based on real table names could lead the model to query tables that do not exist in an uploaded database. |
| 2026-10-02 | Score the evaluation by comparing result data, not SQL text; column names and aliases are ignored | Many different queries are correct for one question; what matters to the user is the data that comes back. |
| 2026-10-02 | Extra predicted columns are allowed as long as every gold column and the row count match; the number of extra columns is recorded | A helpful extra column (e.g. a name next to a count) is not a wrong answer; recording it keeps the scoring transparent. |
| 2026-10-02 | Numbers match within 0.005 absolute or 0.01% relative; NULL and NaN are equal; text is trimmed and case-sensitive; row order only counts for ranking questions | Money is rounded to 2 decimals by the agent, and different SQL can sum in a different order; a stricter check would fail correct answers. |
| 2026-10-02 | Every read-only connection sets `PRAGMA trusted_schema = OFF` | Uploaded SQLite files are untrusted: with the setting off, views, triggers and defaults stored in the file cannot call functions with side effects. Olist has no views or triggers, so its queries and reports are unchanged (checked byte for byte). |
| 2026-10-02 | Reading the schema has a 10 s time limit and fails with a clear error instead of returning a partial schema | A partial schema would make the model write SQL against tables it cannot see. Olist takes about 0.03 s, so the limit only matters for large uploaded files. |
| 2026-10-02 | The schema text in the agent prompt is limited to 12,000 characters, shortened in a fixed order (samples, descriptions, extra columns, extra tables) with a note on what was left out | Keeps prompts within a predictable size for wide uploads while keeping keys, which joins depend on. Olist (about 5,600 characters) is not affected. All limits are named constants in `shared/schema.py`. |
| 2026-10-02 | The evaluation questions are a held-out set; a test fails if a question or its gold SQL appears in the agent prompts or dataset profiles | Questions the model has seen as examples would measure memorization, not how well the agent answers new questions. |
| 2026-10-02 | Every gold query is verified by a second, independently written query, and the verified result is stored in questions.json (`python -m evaluation.verify_questions`) | A wrong gold answer would silently mark correct predictions as failures; the stored result also shows when the data changes. |
| 2026-10-02 | Gold queries return only the columns the question asks for; ambiguous questions accept a clarifying question or any listed reading; requests to change data must be refused | Scores the agent on what the user asked, not on output format, and does not penalize asking when a question really has several meanings. |
| 2026-10-02 | Late delivery compares the delivery date with the estimated delivery date (dates, not timestamps), and the question is marked ambiguous | The estimate has no time of day, so a timestamp comparison counts orders delivered on the estimated day as late (8.11% vs 6.77%). |
| 2026-10-02 | The evaluation runner turns the fallback LLM provider off | A run must measure one model; a silent switch to the fallback would mix two models in one score. |
| 2026-10-02 | LLM outages (quota, server errors) and failing reference queries are "not scored" and left out of the accuracy; `--resume` asks those questions again | They say nothing about the agent's SQL; counting them as wrong would make the score depend on the free-tier quota. |
| 2026-10-02 | Every failure gets one type (wrong values, wrong row count, missing columns, row order, SQL error, unnecessary clarification, wrongly refused, not refused), and questions carry skill tags | Types and skills show where the agent fails (for example the revenue rule or join fan-out), not just how often. |
| 2026-10-02 | Results are written to `evaluation/results/` after every question and are not committed; each file stores the provider, model, profile and a hash of the questions | An interrupted run loses nothing, runs stay comparable, and generated files stay out of the repository like `reports/output/`. |
| 2026-10-02 | A "no-rules" profile (Olist without its business rules and examples) can be evaluated next to the normal profile | Measures how much the business rules in the profile improve accuracy. |
| 2026-10-02 | Dashboard pages are a registry: one file per page in `dashboard/views/` with `VIEW = View(...)`, found automatically | Adding a page is a one-file change and `app.py` stays the same; the folder is not called `pages/` because Streamlit would treat that name as its own multipage app. |
| 2026-10-02 | The dashboard's current data source (database path + dataset profile) is decided only in `dashboard/context.py` and passed to every page | The chat page works the same for the Olist demo and, later, uploaded databases; the report and evaluation pages explicitly use the Olist demo. |
| 2026-10-02 | Navigation is a sidebar menu instead of `st.navigation` | `st.navigation` needs a newer Streamlit than requirements.txt allows; a sidebar radio works on every supported version and is easy to test with AppTest. |
| 2026-10-02 | The chat page keeps one conversation per data source and passes it as `history`, so replies to clarifying questions are understood | Follow-up answers ("2017") only make sense together with the earlier question. |
| 2026-10-02 | Usage stats come from a local JSONL log (`dashboard/usage_log.jsonl`, not committed); for uploaded databases the question text is not stored | Simple, needs no database or account, and keeps uploaded data out of the log. |
| 2026-10-02 | The evaluation write-up reports repeated runs (3 for the main setup) and does not change the question set after seeing results (a correct answer with different row labels stays a failure and is listed as a near-miss) | Shows whether a failure is systematic or random, and keeps the test set independent of the models it measures. |
| 2026-10-02 | Every number in the case study comes from a query on the full database or from an evaluation results file | The documentation can be checked and stays consistent with the reports and the evaluation. |
| 2026-10-02 | Explanations name the actual period when the question uses a relative one ("last month" -> "July 2018"), for every profile including Olist; the SQL also returns the period it resolved to | A relative period is resolved from the data, not from today, so the user needs to see which period the answer covers. The explanation only sees the result, so the period must be in it: without that rule the model guessed a wrong year in testing. Both Olist prompts gain one rule each. |
| 2026-10-02 | `build_user_db` returns an `UploadedDatabase` (path, profile, tables, notes) instead of only a path | The upload page needs the profile to create the agent and the notes to show the user what was changed, so one call gives everything. |
| 2026-10-02 | Uploaded CSV types are inferred strictly: a number or date only if every non-empty value is one; numbers with leading zeros stay text | A wrong type silently breaks answers (e.g. zip codes losing their leading zero, or a mixed column becoming NULLs). Text always keeps the original value. |
| 2026-10-02 | Ambiguous upload dates (e.g. 03/04/2023) default to day/month, with an optional `dayfirst` argument and a note either way | Day/month is the more common order outside the US; values with a day above 12 always decide the order, and the note makes the assumption visible. |
| 2026-10-02 | Table and column names from uploads are cleaned to snake_case; SQL keywords get a `_` suffix and leading `_` is removed | The model writes simpler, valid SQL without quoting, and names starting with `_` would be hidden as internal tables. |
| 2026-10-02 | Upload profiles list each date column's range as a rule but set no `date_range` | `date_range` tells the model the data is complete for that period, which cannot be known for a user's file; the generic latest-date rule applies instead. |
| 2026-10-02 | Upload limits: 50 MB in total (checked before reading), 10 files, 1,000,000 rows and 200 columns per file | Keeps building and describing the database within a few seconds and the schema text within its limit; the size check avoids loading oversized files into memory. |
| 2026-10-02 | SQLite uploads are copied, checked with the file header and `PRAGMA quick_check`, and rejected if they contain views, triggers or virtual tables | An uploaded database is untrusted: views and triggers can run code when tables are read or renamed, and virtual tables may need modules that are not available. Most exported data files have none of these. |
| 2026-10-02 | Table and column names in SQLite uploads are cleaned in the copy with the same rules as CSV headers | One naming style for every upload, simpler SQL from the model, and tables starting with `_` would otherwise be hidden as internal. Renaming in our own copy is safe because triggers and views were rejected first; foreign keys follow the renames. |
| 2026-10-02 | A SQLite file must be uploaded on its own and is limited to 100 tables, plus the same row and column limits as CSV files | Mixing a database with CSV files would need table merging rules that nobody has asked for; the limits keep describing the database fast and the schema text small. |
